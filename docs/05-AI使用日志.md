# AI 使用日志（阶段一）

> 本文件按要求真实记录第一阶段开发过程中使用 AI 编程工具的关键过程：用了什么工具、用什么提示词、得到什么结果、是否修改、改了什么。未逐条记录的琐碎补全（如 import、Getter/Setter）不在此列。

**使用工具**：Trae IDE 内置 AI 编程助手（TraeCode / Claude 系列模型），以对话方式生成与修改代码，并在 IDE 内直接运行 Maven、访问浏览器验证。数据库、运行环境由本人准备（本地 MongoDB 27017）。

---

## 1. MongoDB Schema 设计

**Prompt**：请为"类问卷星"的在线问卷系统设计 MongoDB 集合结构。要求：支持用户注册登录、问卷含多种题型（单选/多选/文本/数字）、题目级约束、选项级跳转逻辑、逐题保存草稿、统计结果；不要把逻辑写死在代码里，后续要能方便地加题型和加条件算子。

**AI 结果**：给出 3 个集合的方案——`users`、`surveys`（题目/选项/约束/跳转规则全部内嵌）、`responses`（答案数组内嵌，含 `currentQid` 支持续填）。

**是否修改**：修改。
- 题型号 `type` 原方案用 Java 枚举 `QuestionType`，改为**字符串**并在 `QuestionTypes` 里配常量。原因：作业要求"逻辑不写死"，枚举每次加题型都要改公共枚举类，字符串 + 处理器注册表扩展更干净。
- 原方案为每道题建了独立集合 `questions`，改为**内嵌数组**。原因：题目与问卷是强聚合、总是整卷读写，内嵌后一次查询即可取得整卷，且数组顺序天然表达答题顺序；独立集合还要额外维护顺序字段。
- 加 `schemaVersion` 字段。原因：第二阶段需求变更时要迁移文档结构，需要版本号做依据。

## 2. 题型与算子的扩展点

**Prompt**：现在有四种题型，每种的结构校验、答案校验、统计都不一样。我不希望 Service 里出现大量 if/else 判断题型。有没有更好的设计？另外跳转条件的算子（等于、包含、大于…）以后还会增加。

**AI 结果**：建议 `QuestionTypeHandler` 接口 + 各题型实现类 + Spring 注入 `List<Handler>` 建注册表；算子用 `Map<String, BiPredicate<Answer,Object>>` 注册表。

**是否修改**：修改。
- 抽出 `AbstractQuestionTypeHandler` 统一处理"三个值字段全空即未作答 + required 报错"的公共逻辑，否则四个实现类里重复代码很多。
- 新增 `core/Values` 工具类。原因：JSON 请求体里同一数值字段可能是 `Integer` 也可能是 `Double`，布尔可能是字符串 `"true"`，AI 初版在多个算子里重复写类型判断，抽取后统一。
- 在 `ConditionOperators.test()` 中加"空答案一律 false、未知算子抛 400"的约定。

## 3. 跳转逻辑引擎与校验

**Prompt**：跳转规则要存在问卷文档里、不能写死在代码里。请实现"答完一题后计算下一题"的逻辑，并考虑：多条规则同时命中怎么办、规则指向不存在的题怎么办、会不会出现死循环、提交时怎么校验才严谨。

**AI 结果**：给出 `LogicEngine.firstQuestion/nextQuestion`，"按规则顺序取第一条命中，未命中则顺序下一题，最后一题返回 null"。

**是否修改**：修改。
- 增加"第一次命中的规则优先"的显式约定并写进注释（AI 初版没说明多规则冲突时的行为）。
- 增加 `validateRules()`：校验规则 id 非空、条件题/目标题存在、算子已注册、动作为 `jumpTo`/`end`；并**强制阶段一只允许向后跳**（目标题下标 > 条件题下标），借此从设计上排除死循环。
- 提交校验改为"从第一题沿跳转路径逐题复核"，而非只校验数组里存在的答案——这样才能保证被跳过的必答题不误报、路径上的必答题漏答能被拦下。

## 4. 脏数据清理（AI 没考虑到，本人补的）

**发现**：手工测试时先答第 1 题选 A（跳到第 5 题）并答了第 5、6 题，再回头把第 1 题改选 B，此时路径变成"第 1 → 第 2 题"，但第 5、6 题的旧答案仍留在答卷里，统计里会混入不该存在的答案。

**修改**：在 `ResponseService.saveAnswer` 中，保存新答案前删除该题及其位置之后的所有旧答案（`indexOfQuestion(a.getQid()) >= answeredIndex`），并补了对应的自动化测试 `answeringEarlierQuestionDiscardsLaterAnswers`。

## 5. 前端页面的 Thymeleaf 报错（AI 生成的代码有 bug）

**现象**：编辑器页面 `GET /surveys/{id}/edit` 返回 500，日志报
`Could not parse as expression: "'eq', '选中'], ['in', '选中其中之一'" (template: "edit" - line 26)`。

**Prompt**：这个页面 500 了，日志说模板表达式解析失败，帮我定位。

**原因**：AI 生成的模板在 `<script th:inline="javascript">` 内写了 JavaScript 二维数组 `[['eq','选中'],...]`。Thymeleaf 的内联 JavaScript 模式会把 `[[ ... ]]` 当作内联输出表达式解析，因此 `single: [['eq', ...]]` 因为紧挨着的 `[[` 被误当成表达式开头。

**修改**：不再只为注入一个变量就开启 `th:inline`，三个页面（`edit.html`/`fill.html`/`stats.html`）统一改为**用隐藏域传值**：模板里写 `<input type="hidden" id="surveyId" th:value="${surveyId}">`，脚本里 `const SURVEY_ID = document.getElementById('surveyId').value;`。这样脚本区域不再有内联解析，彻底避免同类问题。

## 6. 测试依赖与配置（AI 给的版本/配置有两处错）

**问题 a**：AI 起初给的测试依赖版本是 `de.flapdoodle.embed.mongo.spring31x:6.0.0`，Maven 报该版本在阿里云镜像不存在。
**修改**：通过 `mvn` 报错信息确认可用版本，改为 `4.11.0`。

**问题 b**：AI 建议测试配置里不写版本号（认为会自动匹配），但该版本库的自动配置实际要求必须显式提供版本，实测报
`IllegalStateException: Set the de.flapdoodle.mongodb.embedded.version property or define your own IFeatureAwareVersion bean to use embedded MongoDB`。
**修改**：在 `src/test/resources/application.yml` 中显式设置
`de.flapdoodle.mongodb.embedded.version: 6.0.5`，并把测试库名设为 `surveydb_test` 与开发库隔离。

## 7. 环境相关问题（非 AI 错误，记录备查）

- 本机 PowerShell 不支持 `&&` 连接命令，改用 `;`，相关命令均由 AI 生成后修正。
- 命令默认在受限沙箱中执行，而 Maven 本地仓库位于 `D:\apache-maven-3.9.4\mvn_repo`（沙箱可写目录之外），导致下载插件报 `AccessDeniedException`，故 `mvn test` 需在非沙箱模式下运行。
- 浏览器自动化子代理多次超时无法建立会话，端到端页面验证改为：后端 MockMvc 集成测试覆盖完整业务链路 + `Invoke-WebRequest` 验证页面 HTTP 200。

## 8. AI 使用小结（详细评价见项目完成报告）

- AI 承担了约 80% 的代码量：骨架（pom.xml、application.yml、启动类）、模型层、四种题型处理器、算子注册表、Service、Controller、五个 Thymeleaf 页面、共享 CSS/JS、测试代码与文档初稿。
- AI 出错的地方集中在：Thymeleaf 内联表达式与 JS 数组冲突（页面 500）、测试依赖版本与内嵌 Mongo 配置、不写版本号会直接启动失败、以及**架构建模层面漏掉了"改答前面题目导致后续旧答案残留"这一场景**。
- 本人做的主要工作：确定数据库三个集合与内嵌/引用的划分理由、要求"题型与算子不得写死"并据此确定处理器与注册表方案、补上脏数据清理逻辑与向后跳限定、修复页面 500 与测试配置、逐条跑通测试并把每一步失败原因记录在案。

# AI 使用日志（阶段二：题库与版本扩展）

## 9. 扩展方案选型

**Prompt**：需求变更要求题目独立保存复用、共享、修改不影响已建问卷、版本历史与恢复、多版本并存、使用情况、题库管理、跨问卷统计。请给出基于现有三集合结构的扩展方案，要求第一阶段的校验/跳转/统计逻辑尽量不动。

**AI 结果**：采用"版本不可变 + 问卷快照"方案——新增 `question_items`（条目元数据）与 `question_versions`（不可变版本，`parentVersionId` 构成版本链），问卷内嵌题目保留原字段作快照并新增 `itemId/versionId/version` 引用字段；保存问卷时由 `resolveQuestions` 自动判定"新题入题库 / 内容未变沿用版本 / 改自己的题产生新版本 / 改别人的共享题 fork 新条目"。

**是否修改**：修改。
- 恢复旧版改为"以旧版内容创建最新版本"而非回滚指针。原因：回滚会让引用较新版本的问卷突然变成旧内容，违背需求三；新建版本则历史链完整、语义清晰。
- 跨问卷统计按版本分组聚合，仅文本/数字题（且各版本同型时）给跨版本总览。原因：选择题选项 oid 可能随版本变化，直接合并会把不同选项的票数混在一起。

## 10. AI 初版实现的两处疏漏（本人修复）

- **只改标签也刷版本**：`ItemService.update` 起初以"字段是否在请求中出现"判定内容变化，而题库编辑表单总是带上全部内容字段，导致只改标签也会产生新版本。修复为与当前版本做内容比对（`sameContent`），真正不同才建版本，并补测试 `tagsOnlyUpdateDoesNotCreateVersion`。
- **题库表单丢失选项 oid**：编辑表单的选项列表起初只存文本，保存时重新生成 oid，导致内容比对永远不一致、每次保存必出新版本。修复为表单选项保留 `{oid, text}`，并补"清空约束可生效"（非单选题始终提交 constraints）。

## 11. 测试乱码问题（环境问题，记录备查）

**现象**：新增 ItemApiTest 中 7 个用例失败，中文断言全部乱码（`expected:<第一版> but was:<ç¬¬ä¸€ç>`），并连锁导致"内容比对失败 → 多出版本"的断言失败。

**定位**：MockMvc 的 `content(String)` 与 `getContentAsString()` 默认按 ISO-8859-1 编解码；阶段一用例中文断言少且多用 jsonPath（内部按 UTF-8 解析字节）所以未暴露。

**修改**：测试统一改用 UTF-8——请求体用 `writeValueAsBytes` 或 `getBytes(StandardCharsets.UTF_8)`，响应用 `getContentAsString(StandardCharsets.UTF_8)`。修复后 62 个用例全部通过。
